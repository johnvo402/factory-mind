# 0029 - Introduce warehouse inventory ledger

- **Decision:** Replace the free-form inventory snapshot with tenant-owned `Warehouse`, immutable `InventoryTransaction`, and materialized `InventoryBalance` records. This supersedes decision 0024.
- **Why:** A balance answers how much stock exists but cannot explain why. The transaction ledger records receipts, issues, adjustments, transfers, production consumption, and production output. Transaction quantity is always positive; the domain's single `ToSignedQuantity` method resolves direction from the strongly typed transaction type.
- **Balances:** Keep one balance for `(CompanyId, WarehouseId, MaterialId)` instead of summing the complete ledger on every screen, dashboard, or RAG query. Endpoints never create, edit, or delete balances directly; an inventory operation writes the ledger entry and updates the balance together.
- **Atomicity and concurrency:** `EfInventoryRepository` opens an EF Core database transaction for every operation. Increases use PostgreSQL `INSERT ... ON CONFLICT DO UPDATE`; decreases use one conditional `UPDATE ... WHERE Quantity >= requested`. A zero-row update returns the insufficient-stock conflict and writes no transaction. PostgreSQL row locking around the conditional update makes concurrent decrements serialize without a distributed lock. Transfers conditionally decrement the source, upsert the destination, insert both correlated ledger entries, and commit once.
- **Transfers:** `TransferOut` and `TransferIn` have the same generated `ReferenceId`, material, quantity, and tenant. Source and destination must be distinct, active warehouses owned by the authenticated tenant.
- **Tenant isolation:** Company identity comes only from `ICurrentUser`. Handlers resolve warehouses and materials with that company ID, repositories scope every balance/history query by it, and no inventory request accepts `CompanyId`.
- **Migration:** Migration `IntroduceWarehouseInventoryLedger` deterministically converts each distinct legacy `(CompanyId, Warehouse string)` to an active `WH-LEGACY-###` warehouse ordered by name. Existing inventory IDs and quantities become balance rows. Every positive legacy quantity receives an `AdjustmentIncrease` opening transaction with `ReferenceType = LegacyInventoryMigration`; zero balances remain valid without a fabricated positive transaction. The old table is dropped only after the copies complete. The down migration reconstructs snapshots from current balances.
- **Safe warehouse removal:** `DELETE /api/warehouses/{id}` deactivates a warehouse. Warehouse rows are retained because balances and ledger history use restrictive foreign keys.
- **Scope:** No BOM, lots, serials, bins, reservations, costing, purchase orders, sales orders, or production automation are introduced.
- **Date:** 2026-08-28
